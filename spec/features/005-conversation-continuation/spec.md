# 005 - Conversation Continuation

**Status:** Planning

## What makes

This feature lets Flora *remember what was said*. Until 005 every `/chat` call was a blank slate — Flora answered each message with no recollection of the previous one, so the user's phrase "como te decía…" landed on silence and every follow-up needed its context re-stated. 005 turns `/chat` into an ongoing conversation: the agent stores messages in the existing `ai_conversations` / `ai_messages` tables (already RLS-protected, already in place — no new schema) and loads the recent history of the active conversation into the Gemini context window before answering. The companion stops being a goldfish.

The posture change is deliberate and is the one V1.0 hard limit 005 lifts: **`/chat` stops being side-effect-free.** 003 guarded writes by keeping `/chat` read-only and routing mutations through a separate `/actions/execute`; 005 keeps that mutation contract *for user-facing actions* (`proposed_action` / `confirm_token` are untouched) but adds a *new* class of write that is intrinsic to the conversation itself — persisting the two messages that just happened. This is not a user action and never goes through the propose → confirm flow: storing the user's own words back to the user's own conversation is not something the user would meaningfully consent to per turn. RLS under the caller's token is the fence, same as 002/003; the difference is that `/chat` now leaves a row behind.

Concretely it delivers:

- **`conversation_id` becomes the spine of the conversation.** `/chat` accepts an optional `conversation_id`. When present, the message belongs to that conversation and its recent history is loaded. When absent, the agent **auto-creates** a new conversation for that first message and returns its `conversation_id`, so the simple "just chat" path still works. The `POST /chat` response therefore gains a required `conversation_id` field — every reply now tells the client which conversation it lives in, so the app can thread subsequent messages. There is no stateless mode left; persistence is the default and is the whole point of 005.
- **A dedicated create endpoint — `POST /conversations`.** For the UX where the app wants to start a conversation explicitly (e.g. "ask Flora about this plant" → open a fresh thread tied to a plant), `POST /conversations` takes an optional `plant_id` and `title` and returns a fresh `conversation_id`. The app then attaches it to `/chat`. This is the path the roadmap item "POST endpoint that returns a `conversation_id`" calls out; auto-creation on `/chat` is the forgiving fallback.
- **Message persistence on every `/chat` turn.** On each call the agent:
  1. resolves the conversation (loads it by `conversation_id` under the caller's RLS-scoped client; `404 CONVERSATION_NOT_FOUND` if the id is foreign or absent-under-RLS — a foreign id is provably "not yours" and is **not** silently turned into a new conversation, because that would duplicate threads and hide a client bug),
  2. loads the conversation's recent `ai_messages` (see history, below),
  3. **persists the user message first** — so it survives even if the Gemini call fails (the user can retry into a saved history),
  4. builds 002's deep/light plant context + the conversation history, calls Gemini (existing `call_gemini` + 003/004 structured response), and
  5. **persists the assistant reply** on success, then **bumps `ai_conversations.updated_at`**.
  Storage goes through the **user-scoped** Supabase client (the same one 002/003 use); `ai_conversations` is inserted with `user_id = user.sub` (the RLS `WITH CHECK (auth.uid() = user_id)` policy requires the value the agent supplies to equal the caller), and `ai_messages` rows carry only `conversation_id` / `role` / `content` / `photo_url` (the table has **no** `user_id` column — ownership is inferred via the FK to the conversation, which RLS guards). The agent never sets a `user_id` it didn't get from the verified token. `ai_messages.content` has a database `CHECK (char_length BETWEEN 1 AND 4000)`; the assistant reply is defensively truncated to 4000 chars before insert (the user's message is already ≤ 2000 by `/chat` validation).
- **Conversation history loaded into the Gemini context window.** Before the user's current message is sent to Gemini, the agent fetches the last N messages of the active conversation (chronological, oldest→newest, where N is a configurable `history_max_messages`, default 20) and injects them into the context block as a clearly-labelled "Historial de la conversación" section — `Usuario:` / `Flora:` turns — **before** the 002 plant context and the current message. History is the chat-specific layer; 002's deep/light plant context is the garden-specific layer; both coexist. The current user message is **excluded** from the loaded history (it is the active turn, not a recalled one), so it never appears twice in the prompt. A `proposed_action` / `vision_request` produced in a prior turn **is not** replayed as history text — only the turn's `reply`/content is persisted to `ai_messages`; proposed-action tokens are short-lived (003) and vision asks are side-effect-free (004), so neither survives into the next turn's context as text. This keeps history clean and avoids re-arming expired action tokens.
- **Token budget on history.** History length is capped two ways: a configurable **message count** (`history_max_messages`) and a configurable **character budget** (`history_max_chars`) applied to the combined history block. When the budget is exceeded the agent trims from the **oldest** messages first (drops the least-recent turn and retries), so the most recent context always fits — consistent with "remember what was said *recently*", not "remember everything forever". Both knobs live in `app/config/settings.py` and default to values that comfortably stay within the configured model's context window alongside 002's deep context.
- **List the user's conversations — `GET /conversations`.** Returns the authenticated user's conversations (id, title, plant_id, updated_at, created_at), ordered by `updated_at` desc, capped at a configurable `conversations_max_results` (default 50). Runs through the user-scoped client so RLS scopes it; an empty garden returns `200 []`. This is the endpoint the app uses to show a "past conversations" list ("tus charlas con Flora").
- **Get a conversation's messages — `GET /conversations/{conversation_id}/messages`.** Returns the full `ai_messages` list for that conversation, oldest→newest (role, content, created_at, photo_url). A `conversation_id` the caller doesn't own (RLS returns no conversation row) → `404 CONVERSATION_NOT_FOUND`, consistent with the 004 retrieval reasoning (RLS turns "not yours" into "doesn't exist"). This is the endpoint the app uses to resume a thread.
- **Auto-title.** When a conversation is created (explicit `POST /conversations` with a provided `title`, auto-created on `/chat`, or creation without a title), a short Spanish title is derived **from the first user message** and stored on the `ai_conversations.title` column — falling back to the column's existing default `'Conversación con Flora'` when there is no first message yet (the explicit-create-then-chat path). In V1.0 the title is produced **locally** (no extra Gemini call — cost and latency discipline matching 004's ethos): the first user message is trimmed to a configurable `conversation_title_max_chars` (default 48) at the last whole-word boundary ≤ the cap, with a trailing `…` when truncated. The agent does *not* call Gemini to title conversations; an LLM-summarised title is flagged as a backlog idea, not a V1.0 item. The auto-title is set on the conversation's first persisted user message (update in place) and is not regenerated on later turns — the thread's title reflects how it started, like a chat thread title.
- **Plant scoping.** A conversation may optionally link to a `plant_id` (`ai_conversations.plant_id` is nullable). The link is established on creation: `POST /conversations` takes `plant_id`; auto-creation on `/chat` inherits the request's `plant_id`. Once a conversation has a non-null `plant_id`, a subsequent `/chat` carrying a *different* non-null `plant_id` returns `400 CONVERSATION_PLANT_MISMATCH` rather than silently rewriting the thread's scope — a conversation belongs to at most one plant. A conversation with a null `plant_id` may be scoped on its first plant-bearing `/chat` (the agent sets `ai_conversations.plant_id` via an RLS-guarded update); thereafter it is fixed. The 002 context builder already keys off `plant_id`; 005 ensures the conversation's `plant_id` (not just the per-turn request) is what scopes deep context, so a resumed plant thread re-loads that plant's living memory even if the app forgets to send `plant_id` on every turn.
- **Privacy and audit (unchanged posture, restated for persistence).** Logs stay content-free: the agent logs counts, durations, `conversation_id` (a uuid, not identifying beyond the user the request already authenticates), `user.sub`, and status — **never** message `content`, never `title` (a title is a derived snippet of content). This matches the 002/003/004 convention ("only counts/durations, never contents"). The content now durably lives in the user's own RLS-scoped `ai_messages`/`ai_conversations` rows — which is exactly where the user expects their conversation to live. A structured audit event is emitted on each `/chat` persist (success and 502 failure) and on each new conversation, with scalar fields only.
- **Contract & docs.** `docs/api-contract.md` documents the new `conversation_id` on the `/chat` request/response, the `POST /conversations` and `GET /conversations` and `GET /conversations/{id}/messages` routes, the new `conversation_id` field on `/chat`, the `title` derivation rule, the plant-mismatch and not-found error codes, and the cost-gating-by-history-budget rule. `tech-stack.md` gets the new persistence posture in the file map (`app/conversations/` module), the new settings (`history_max_messages`, `history_max_chars`, `conversation_title_max_chars`, `conversations_max_results`), and reframes the "No conversation persistence" hard limit as lifted by 005.
- **Tests** for the new behaviour: `/chat` persists both messages through the user-scoped client and asserts `user_id` on the conversation insert equals `user.sub` and is never taken from the body; `/chat` without `conversation_id` auto-creates a conversation and returns its id, and the next `/chat` with that id loads the prior turn as history (assert by inspecting the mocked Gemini `contents`); `/chat` with a foreign/unknown `conversation_id` → `404`; history load is capped (message count and char budget, oldest-first trim); the current message is never duplicated in the history block; assistant content > 4000 is truncated before persist; a Gemini 502 leaves the user message stored and the assistant row absent; `POST /conversations` creates a conversation scoped to the optional `plant_id`; `GET /conversations` returns the user's threads ordered by `updated_at` and scoped by RLS (foreign user → empty); `GET /conversations/{id}/messages` returns the full thread, foreign id → 404; auto-title is derived from the first user message and respects the char cap and word boundary; plant-mismatch → 400; a null-plant conversation is scoped by its first plant `/chat`; the full 001/002/003/004 regression suite still passes with persistence in flight (auth 401, context RLS deny, propose/confirm/execute, vision `vision_request`, off-topic refusal, Spanish-only, text-only `/chat`).
- **A reconciled constitution.** `tech-stack.md` lists `app/conversations/`, the new settings/env vars, and reframes the V1.0 "No conversation persistence" hard limit as lifted by 005 (matching the reconciliation pattern 001–004 used).

## Why

The companion promise in `mission.md` is that Flora "knows the complete history of every plant" and "considers… previous photos, plant evolution, user notes, watering history…" before responding. 002 gave her the *plant's* history. But the *conversation's* history — the very thing that makes a chat feel like talking to a friend who remembers what you just said — was a deliberate Non-Goal until now, and 003 leaned on it heavily: 003's "save-a-tip" flow exists *because* "the conversation disappears" (the Non-Goal, restated in 003 spec) and a useful tip needed rescuing before it evaporated. 005 is the feature that retires that Non-Goal.

Concretely, without 005: the user asks "¿cada cuánto riego mi Monstera?", Flora answers with the reasoning, the user follows up "y si está cerca de una ventana?", and Flora — having no idea which plant "una ventana" refers to, or that "y" means "in addition to the schedule you just proposed" — answers generically or asks "¿de qué planta hablas?" That goldfish moment is exactly the "confusing" and "unreliable" failure `mission.md` says the app must never be. It also undermines 003: a `proposed_action` like "crear riego cada 7 días" is offered, but if the user wants to tweak it ("hazlo cada 10 en cambio"), the second turn has lost the first; the propose/confirm loop forces a re-state. Persisting the conversation closes the loop Flora's persona was written to assume.

005 lands *now* — after 004 — for two reasons. First, the prerequisites are already in place: the `ai_conversations` / `ai_messages` tables and their RLS policies already exist and are unused, so 005 is a pure *behaviour* feature (no schema migration, no new RLS design) on top of the verified 002 read path and 003 write-identity path — it's the lowest-risk high-value feature left. Second, the flashier features still ahead (006 dynamic states, 007 web search) will produce multi-turn reasoning whose value collapses without memory: a web-search-grounded answer the user can't follow up on with "¿y eso del sol qué significa?" is half a feature. 006/007 are built to assume a persistent thread.

The dominant design axis is **the one posture change 003 fought to preserve**: `/chat` stops being side-effect-free. The architecture is built around making that change safe and unsurprising: writes are scoped to the two tables the feature is named after, ownership is RLS-under-the-caller's-token (never a service-role key, never a `user_id` from the body), the current message is never duplicated into context, history is budgeted so cost stays bounded and predictable, and the mutation contract 003 defends (propose → confirm → execute for *user-facing* actions) is left entirely intact — persistence is a different, lower-stakes class of write that belongs to the conversation itself. The user never experiences "Flora remembered"; they just stop experiencing "Flora forgot."

## Acceptance criteria

- `POST /chat` persists exactly one `user` `ai_messages` row and exactly one `assistant` `ai_messages` row per successful call, both through the **user-scoped** Supabase client (asserted in tests: the write uses `user.access_token`, never a service-role key), both with `conversation_id` equal to the request's `conversation_id` (when provided) or to a newly-created conversation's id.
- `POST /chat` response includes a required `conversation_id` (uuid string) field; when the request omitted `conversation_id`, the value is the id of a newly-created `ai_conversations` row whose insert supplies `user_id = user.sub` (assert: the agent passes `user_id` equal to the verified `sub`, never a value from the body); when the request supplied `conversation_id`, the value matches it and no new conversation is created.
- `POST /chat` with a `conversation_id` that does not exist or belongs to another user (RLS returns no row under the caller's token) returns `404 CONVERSATION_NOT_FOUND` and performs **no** Gemini call and **no** message persistence; it never silently creates a new conversation for an unknown id.
- `POST /chat` with a `conversation_id` whose conversation has a non-null `plant_id`, and whose request carries a non-null `plant_id` that differs, returns `400 CONVERSATION_PLANT_MISMATCH` and performs no Gemini call and no persist.
- `POST /chat` whose conversation has a `plant_id` (set on creation or first scoping) loads 002 deep context for **that** plant even when the request omits `plant_id` (the conversation's scoping is the source of truth); the 002 deep-context tests still pass against a resumed thread.
- A second `POST /chat` in the same conversation causes the first turn's user message and assistant reply to appear in the Gemini `contents` as a labelled "Historial de la conversación" block (assert by inspecting the mocked Gemini call), in chronological order, **before** the 002 context block, and the current message appears exactly once.
- The history block respects `history_max_messages`: when more than that many messages exist, only the most recent N-1 prior turns are included (oldest trimmed), and the current turn is excluded from the loaded set. The block respects `history_max_chars`: when the combined history text exceeds the cap, the oldest turns are dropped until it fits; the most recent context always survives.
- On a Gemini `502 UPSTREAM_ERROR` mid-`/chat`, the **user** message has already been persisted (asserted: the `user` row exists, the `assistant` row does not), and the response is the existing `502` envelope (no `conversation_id`-creation regression). A retry with the same message does not double-persist the prior user turn (the prior turn is history, the retry is a new `user` row — both kept, ordered by `created_at`).
- `ai_messages.content` persisted by the agent always satisfies the database `CHECK (char_length BETWEEN 1 AND 4000)`: the user message (already ≤ 2000 by `/chat` validation) is stored whole; an assistant reply longer than 4000 chars is truncated to 4000 (with a trailing `…`) **before** insert — asserted with a mocked long Gemini reply that the stored `content` is exactly 4000 chars long. Neither table insert ever supplies a `user_id` from the request body.
- After each successful `/chat` persist, the conversation's `ai_conversations.updated_at` is greater than its `created_at` (the agent explicitly bumps it; no trigger exists) — asserted; the `GET /conversations` ordering by `updated_at` reflects activity, not creation order.
- `POST /conversations` with a valid `Authorization` header and an optional `plant_id`/`title` returns `201 {"conversation_id": "..."}` (or `200`; the contract locks the status code in `plan.md`) and creates a conversation whose `user_id = user.sub` and whose `title` is the provided title or the column default; no Gemini call is made.
- `GET /conversations` with a valid `Authorization` header returns `200 [ {conversation_id, title, plant_id, updated_at, created_at}, ... ]` ordered by `updated_at` desc, capped at `conversations_max_results`; under RLS the list contains only the caller's conversations (a foreign user's conversations never appear — asserted by mocking the client and asserting the select is the user-scoped one). An empty garden returns `200 []`.
- `GET /conversations/{conversation_id}/messages` for a conversation the caller owns returns `200 [ {role, content, created_at, photo_url}, ... ]` oldest→newest (with `photo_url` present in the model but `null` in V1.0 since the agent writes only text turns). For a `conversation_id` the caller doesn't own (RLS returns no conversation), returns `404 CONVERSATION_NOT_FOUND` and no message list.
- Auto-title: the first user message persisted in a conversation whose `title` is still the default produces a `ai_conversations.title` equal to a Spanish-safe truncation of that message at the last whole word ≤ `conversation_title_max_chars`, with a trailing `…` only when truncation occurred (assert: "Hola Flora, ¿cómo va mi Monstera?" at cap 48 stays whole; a 120-char message yields ≤ 48 chars ending in `…`, split at a space). The title is set exactly once (on first user message) and is not regenerated on later turns (assert: a later turn does not update `title`).
- A conversation created with an explicit `title` via `POST /conversations` keeps that title even after the first user message (explicit titles are not overwritten by auto-title).
- Audit: every `/chat` persist (success and 502), every `POST /conversations`, and every list/get emits a scalar-only structured log event (`conversation_id`, `user.sub`, message counts, `status`, `duration_ms`) that **never** contains message `content` or `title` — asserted against captured log records on the happy and 502 paths.
- `docs/api-contract.md` documents the `conversation_id` on the `/chat` request/response, `POST /conversations`, `GET /conversations`, `GET /conversations/{id}/messages` (with their `200`/`401`/`404`/`400` responses), the auto-title rule, the history-budget rule, and the new `404 CONVERSATION_NOT_FOUND` / `400 CONVERSATION_PLANT_MISMATCH` error codes in the error table.
- `spec/constitution/tech-stack.md` lists `app/conversations/`, the new settings (`history_max_messages`, `history_max_chars`, `conversation_title_max_chars`, `conversations_max_results`) and env vars, and reframes the V1.0 "No conversation persistence" hard limit as lifted by 005.
- `uv run pytest` passes, including the new conversation tests and the full 001/002/003/004 regression suite (auth 401, context RLS deny + minimization + 502, `/chat` propose + `/actions/execute` happy/token-lifecycle/allowlist/hash, watering deactivate-then-insert, save-a-tip, `vision_request` text-only `/chat`, image-validator/resize, off-topic refusal, Spanish-only). `uv run ruff check` and `uv run ruff format --check` pass.

## Out of reach

Explicitly out of scope for 005; they belong to later features or the constitution:

- **Conversation deletion / editing.** The DB has `ai_conversations` `DELETE` and `ai_messages` `DELETE` policies, but 005 exposes no delete endpoint. Deleting a thread, editing a past message, or "clear history" is a future surface (it widens the mutable surface RLS-wise and needs its own UX). `GET`/`POST` plus the implicit `/chat` appends are the V1.0 surface; deletes are deferred.
- **Conversation titles via Gemini.** The auto-title is a local truncation of the first user message, not an LLM summarisation. An LLM-generated, more descriptive title is a backlog idea; V1.0 keeps it free and instant.
- **Rewriting / re-summarising the title on later turns.** A thread's title reflects how it started (first user message); it is not regenerated as the topic drifts. Thread-renaming by the user is out of reach (no update surface in V1.0).
- **Multi-plant conversations.** A conversation is scoped to at most one `plant_id` (or none, a general chit-chat). Conversations that roam across plants — or that change plant mid-thread — are out of reach; the `CONVERSATION_PLANT_MISMATCH` guard keeps a thread pinned. A general (null-plant) thread that the user later wants to pin to a plant is scoped only on the first plant-bearing turn and locked thereafter.
- **Persisting `vision_request` / `proposed_action` turns as history text.** Only the conversational `content` (Flora's reply text, the user's message text) is stored in `ai_messages`. The `proposed_action` payload and `vision_request` are not persisted as message rows — they are per-turn extras, ephemeral by design (003 single-use token, 004 side-effect-free ask). A future feature that wants to show "Flora offered to set up watering here" in a resumed thread re-derives it; the raw token/ask does not survive. The `ai_messages.photo_url` column stays `null` in V1.0 (the agent does not write image turns — that would entangle with 004's no-persistence-on-inline path and Storage ownership).
- **Vision-turn persistence (004 interplay).** `/vision/*` endpoints remain side-effect-free with respect to `ai_messages` — they do not append to a conversation thread, even if a `conversation_id` were supplied. Linking a vision diagnosis back into an ongoing conversation thread is a follow-up (it needs a decision about whether a vision turn is a "message"); out of reach for 005.
- **Cross-conversation memory ("Flora remembers across all your chats").** 005 loads only the *active* conversation's history, scoped by `conversation_id`. A global per-plant or per-user memory that synthesises across every conversation is a larger design (privacy, summarisation, cost) and belongs to a later feature.
- **Streaming / dynamic statuses (006).** `/chat` and the new `GET`/`POST /conversations*` routes stay single-shot. The " Flam… está recordando tu última charla" status belongs to 006.
- **Web search grounding of history (007).** History is purely the stored turns; no web-sourced augmentation of memory.
- **A durable audit table.** Audit lives in agent-side structured logs (Cloud Logging), same decision as 003/004; the agent does not own a Supabase audit table.
- **Per-user rate limiting / conversation-count caps.** No per-user rate state exists today; runaway conversation creation is bounded only by RLS ownership and the `conversations_max_results` list cap. A rate limit / quota belongs to the Backlog (it surfaced first in 004's risks and remains deferred).
- **Migration of RLS or schema.** None. The `ai_conversations` / `ai_messages` tables and their RLS policies already exist; 005 adds no migration. (The constitution's "no migration" assumption is verified in `users-tasks.md`.)
