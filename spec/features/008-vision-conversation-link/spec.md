# 008 - Vision Conversation Link

**Status:** Planning

## What makes

This feature bridges 004 and 005 so a vision diagnosis doesn't vanish after it's delivered. Until 008, `/vision/analyze-stored` and `/vision/analyze-upload` are side-effect-free — they return a diagnosis and immediately forget it. The user gets their answer, but if they then ask `/chat` "¿y eso del sol qué significa?", Flora has no idea what "eso" refers to. The vision result never enters the conversation thread.

008 lets the vision endpoints participate in the conversation persistence that 005 introduced. Concretely:

- **Both `/vision/*` endpoints accept an optional `conversation_id`.** When present, the turn is linked to that conversation: the user's message and Flora's reply are persisted as `ai_messages` rows (same two-row, RLS-scoped model 005 uses for `/chat`), and `ai_conversations.updated_at` is bumped. When absent, the vision call remains fully side-effect-free — the 004 behaviour is preserved for callers that don't want threading (health checks, one-off diagnoses, batch tools).
- **Auto-creation on `/vision/*` mirrors 005's `/chat` auto-creation.** When `conversation_id` is absent, the endpoints stay side-effect-free (no auto-create). Auto-creation is **not** offered here — vision is an opt-in conversation participant, not a "just chat" flow. The app opens the conversation first (`POST /conversations`) or starts it via `/chat`, then attaches `conversation_id` to the vision call. **Rationale:** a vision turn without a conversation ID is a one-off analysis; silently creating a thread for it would surprise the client and spawn empty threads. Only `/chat` auto-creates; `/vision/*` threads into an existing conversation or stays stateless.
- **`ai_messages.photo_url` becomes non-null for vision turns.** 005 kept it `null` because `/chat` writes only text. 008 populates it with the analyzed photo's public Storage URL (for stored references) or leaves it `null` (for inline uploads — the image is not persisted and has no URL). This lets a resumed thread show "[El usuario compartió una foto]" in the history block rather than a bare assistant reply with no context.
- **History injection marks photo turns.** When 005's `format_history_block` encounters a message with a non-null `photo_url`, it labels that turn as a photo turn: `Usuario: [Foto] {message}` for the user turn (so Flora knows the user sent an image this turn), and `Flora: {reply}` for the assistant turn (unchanged). Flora can't see the old image on a resumed text turn — Gemini vision requires inline image bytes — so the label tells her *that* a photo was shared without re-sending bytes. A follow-up `/chat` asking "¿y la foto que te envié?" is answered from Flora's textual memory of the diagnosis, not from re-analyzing the image.
- **The structured `vision` analysis is not persisted as history text.** Consistent with 005's decision on `proposed_action` / `vision_request`, the `vision` object (diagnosis, species candidates, confidence) is a per-turn extra returned to the client but not stored as message `content`. Only the conversational `reply` text is persisted. The client can call `GET /conversations/{id}/messages` to replay the thread and gets the `reply` text + the `photo_url` pointer; the structured `vision` data is not part of `ai_messages`. (Future feature: a `GET /conversations/{id}/vision` endpoint that cross-references `ai_messages.photo_url` turns with their original analysis — out of reach for 008.)
- **`proposed_action` from a vision turn is also not persisted as history text.** Same rule as 005. The action token is short-lived; the `reply` text ("Te voy a proponer crear un calendario de riego…") is what survives into history.
- **Plant scoping from 005 carries over.** A vision call with a `conversation_id` whose conversation has a non-null `plant_id` and whose request carries a *different* non-null `plant_id` returns `400 CONVERSATION_PLANT_MISMATCH`. A null-plant conversation can be scoped by its first plant-bearing vision turn (`set_plant_id_once`), locked thereafter — mirroring the `/chat` rule.
- **Reuses the 005 conversation store, audit, and error handling.** `create_conversation` is not called by vision endpoints (no auto-create), but `get_conversation` (404 on foreign id), `append_message`, `bump_updated_at`, `set_plant_id_once`, and `fetch_history` are reused verbatim. The `ConversationNotFoundError` / `ConversationPlantMismatchError` handlers and the `mock_conversation_store` fixture pattern from 005 are reused.
- **History loading on vision turns is optional and lightweight.** When `conversation_id` is present, the vision endpoint loads the conversation's recent history (same `history_max_messages` / `history_max_chars` budget) and injects it into the Gemini vision context as a "Historial de la conversación" block — identical to 005's `/chat` injection. This lets Flora's vision analysis reference prior turns ("como te decía, si las hojas están amarillas…"). The budget and trim rules are the same settings from 005; no new knobs.
- **Audit stays scalar-only.** The `log_vision_call` audit gains a `conversation_id` field (scalar, no content) when the turn is threaded. No vision or image content is logged.
- **No schema migration.** Same as 005 — the `ai_messages` and `ai_conversations` tables already have the columns this feature uses (`photo_url`, `conversation_id`, etc.). 008 is a pure behaviour change on the vision endpoints, layered on the 005 store.

Concretely it delivers:

- **Optional `conversation_id` on `/vision/analyze-stored` and `/vision/analyze-upload`.** When provided, the turn is persisted; when absent, fully stateless (004 behaviour).
- **`VisionAnalyzeResponse` gains a `conversation_id` field (optional, present only when the request supplied one).** Unlike `/chat` where `conversation_id` is *required* in the response (every `/chat` creates or resumes a thread), a stateless vision call returns `conversation_id: null` — the client knows no thread was touched.
- **`photo_url` populated on the user `ai_messages` row for stored vision turns.** For inline uploads, `photo_url` stays `null` (the image is transient).
- **History injection with photo-turn labels on vision turns.**
- **Plant scoping, 404 not-found, and 400 mismatch errors on vision endpoints**, reusing the 005 handlers.
- **Tests, contract updates, and constitution reconciliation.**

## Why

005 retired the "conversation disappears" Non-Goal for `/chat`. But 004's vision endpoints were deliberately excluded from that retirement (`spec.md:74` — "out of reach for 005"): a vision diagnosis is returned to the client but never enters the conversation's living memory.

The product story is the gap that creates: the user photographs yellowing leaves, Flora diagnoses overwatering, offers a watering schedule — a great multi-signal turn. The user then switches to the chat and asks "¿y si la muevo a un sitio con más luz?" Flora has no idea what plant they're talking about, no idea a photo was shared, and no memory of the diagnosis. The vision result is a dead-end; the user must re-state everything they just learned.

Brote's promise is that Flora "knows the complete history of every plant" and "considers previous photos, plant evolution…" — the vision diagnosis is the most information-rich turn in the whole app, and it's the one that evaporates. 008 closes the loop.

005 built the persistence layer (`ai_conversations` / `ai_messages`, RLS, history injection, plant scoping) as a *general* mechanism that 008 can adopt with minimal new code. The dominant work is: add an optional `conversation_id` parameter to the two vision request models, wire the resolve → load-history → persist-user → (existing vision call) → persist-assistant → bump flow (reusing 005's store functions directly), and mark photo turns in the history block. The store, the RLS policies, the error handlers, the auto-title — all exist; 008 is a *consumer* of 005's infrastructure.

## Acceptance criteria

- `POST /vision/analyze-stored` and `POST /vision/analyze-upload` accept an optional `conversation_id` (UUID; 422 on a non-uuid format). When absent, the endpoint behaviour is identical to the pre-008 (004) behaviour — no `ai_messages` rows are written, `ai_conversations` is untouched, the response `conversation_id` field is `null`. When present, the endpoint persists the user message and assistant reply as two `ai_messages` rows through the user-scoped Supabase client, and the response `conversation_id` equals the request's `conversation_id`.
- `VisionAnalyzeResponse` gains an optional `conversation_id: str | None = None` field. When the request provided `conversation_id`, the field carries that value; when absent, `null`.
- On a vision call with `conversation_id` that is foreign/unknown (RLS returns no conversation under the caller's token) → `404 CONVERSATION_NOT_FOUND`, no Gemini call, no persist, no image fetch.
- On a vision call with `conversation_id` whose conversation has a non-null `plant_id` and whose request carries a non-null `plant_id`/`image_ref` plant that differs → `400 CONVERSATION_PLANT_MISMATCH`, no Gemini call, no persist.
- On a vision call with `conversation_id` whose conversation has a null `plant_id` and whose request carries a non-null `plant_id` → `set_plant_id_once` is called (RLS-guarded), the conversation is scoped, and the deep context loads for that plant.
- The conversation's `plant_id` (not just the request's) is the source of truth for 002 deep context on a threaded vision call — identical to 005's rule so a resumed vision thread re-loads its plant even if the app omits `plant_id`.
- For `/vision/analyze-stored` with a threaded conversation: the user `ai_messages` row has `photo_url` set to the resolved photo's Storage URL; the assistant `ai_messages` row has `photo_url = null`. For `/vision/analyze-upload` with a threaded conversation: both rows have `photo_url = null` (the image is transient — no Storage URL to reference).
- On a threaded vision call, the conversation's recent `ai_messages` history is loaded (via 005's `fetch_history` + `trim_to_budget`) and injected into the Gemini vision context as a "Historial de la conversación" block **before** the 002 plant context block. Photo turns are labelled: a user turn with non-null `photo_url` appears as `Usuario: [Foto] {content}` in the history block; an assistant turn appears as `Flora: {content}` (unchanged from 005). The current user message (the vision request's `message`) is not in the loaded history (it is the active turn).
- On a threaded vision call, the user message is persisted **before** the Gemini call (survives a 502), the assistant reply is persisted **after** on success, and `ai_conversations.updated_at` is bumped — identical to 005's ordering. On a Gemini 502, the user row exists, the assistant row does not.
- On a threaded vision call, the assistant `reply` content > 4000 chars is truncated to 4000 with a trailing `…` before insert (reusing 005's store logic).
- `log_vision_call` gains a `conversation_id: str | None` parameter (scalar field only; no content). When `conversation_id` is `null`, the field is absent/`null` in the log record.
- `docs/api-contract.md` documents the optional `conversation_id` on both `/vision/*` requests, the optional `conversation_id` on `VisionAnalyzeResponse`, the photo-turn labelling in history, the 404/400 error reuse from 005, and the "stateless when no `conversation_id`; threaded when present" dual mode.
- `spec/constitution/tech-stack.md` notes that `/vision/*` now participates in conversation persistence when `conversation_id` is supplied (no new module — reuses `app/conversations/`).
- `uv run pytest` passes, including new vision-conversation tests and the full 001–007 regression suite. `uv run ruff check` and `uv run ruff format --check` pass (no new errors beyond the pre-existing set).

## Out of reach

Explicitly out of scope for 008:

- **Auto-creation on `/vision/*`.** Vision is an opt-in conversation participant. If `conversation_id` is absent, the call stays stateless. The app is expected to open the conversation via `POST /conversations` or `/chat` first. **Rejected:** silently creating a thread for a stateless vision call — it spawns empty threads and surprises the client. Only `/chat` auto-creates.
- **Persisting the structured `vision` analysis in `ai_messages`.** Only the conversational `reply` text is stored. The `vision` object (diagnosis, species, confidence, needs_more_info) is a per-turn extra returned to the client but not persisted. A future `GET /conversations/{id}/vision` endpoint could cross-reference `photo_url` turns with their analysis — out of reach for 008.
- **Re-sending image bytes into the history block.** The history block is text-only; photo turns are labelled `[Foto]` but the image bytes are not re-sent to Gemini on a resumed text turn. Flora's memory of the diagnosis is her textual reply, not the image. **Rejected:** storing image bytes in `ai_messages` — entangles with Storage ownership and breaks the text-only history invariant.
- **Inline-upload photo persistence.** `/vision/analyze-upload` images are transient. The `photo_url` column stays `null` for inline vision turns. Persisting the uploaded image to Storage and auto-populating `photo_url` is a separate decision (Storage ownership, cleanup policy) — out of reach.
- **Vision turn auto-titling.** 005 auto-titles from the first user message. 008 does **not** re-derive titles on vision turns — the first turn's title (from `/chat` or `POST /conversations`) stands. If the first turn in a conversation is a vision call, the title stays the default `"Conversación con Flora"` (a vision message about yellow leaves is a poor title anyway; LLM titling belongs to the backlog).
- **Multi-photo turns.** A vision call analyses one image. The `photo_url` column is single-valued. Multi-image analysis is a broader 004 question, not a 008 one.
- **Conversation deletion or editing of vision turns.** Same as 005 — no delete/edit surface in V1.0.
- **Vision endpoint auto-creation of conversations.** See above.
- **Loading the actual stored photo into a resumed `/chat` turn.** When the user asks `/chat` "¿y la foto que te envié?", Flora answers from her textual memory (the diagnosis in the `reply`). She does not re-fetch the stored image for a text `/chat` turn. If the user wants a fresh look, they call `/vision/*` again. **Rejected:** auto-re-fetching `photo_url` referenced images into `/chat` — it couples the text endpoint to Storage and unsolicitedly re-sends bytes to Gemini.
