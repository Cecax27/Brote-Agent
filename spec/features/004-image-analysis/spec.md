# 004 - Image Analysis

**Status:** Planning

## What makes

This feature lets Flora actually *see* a plant — but only when the user wants her to, and never by default. It adds **vision** to the companion without breaking the privacy/cost posture of 001–003. Two distinct intake paths, one shared vision core, and a gating mechanism that keeps images out of Flora's context unless the user explicitly authorizes them.

Concretely it delivers:

- **Two image intake paths (the two functions the user cares about):**
  1. **Retrieve from Supabase.** When a user asks Flora to examine a photo they already have in their plant's journal, the agent resolves that photo through the user's Row-Level-Security-scoped client and downloads the bytes from the existing public `plant-photos` Storage bucket — it never re-decides ownership (the DB lookup under the user's token already proved the row is theirs; a cross-user ref resolves to empty and becomes a `404 IMAGE_NOT_FOUND`). This is the "examina la foto de mi diario" flow.
  2. **Receive an image without storing it.** A user snaps or picks a photo in the app just to ask Flora about it, without it ever landing in Supabase. The agent accepts it as a short-lived multipart upload, validates it, analyses it in memory, and discards it — there is no Supabase write, no local disk write, no blob kept across requests. This is the ad-hoc "mira esta foto" flow.
  Both paths produce the same Flora reply: a Spanish, on-brand, honest answer that can include a diagnosis, a species identification with a confidence indicator, and an optional `proposed_action` (reusing 003's propose → confirm → execute machinery — e.g. "save this diagnosis to your Monstera's journal" or "set a watering schedule").
- **Cost gating — images never auto-enter the context.** This is the central design rule and it drives the whole architecture:
  - `POST /chat` stays **text-only**. It still injects 002's deep/light context — which today surfaces photo *metadata only* (`photo_count`, never bytes or URLs) — and Flora answers from that. No image bytes are ever sent to Gemini on a `/chat` call, regardless of how many photos a plant's journal has.
  - When Flora judges that seeing a photo would genuinely help (a leaf looks off in the user's description, she can't tell yellowing cause from text alone, the user is asking "is this normal?"), she may **ask the user for authorization** by returning an optional `vision_request` alongside her reply: `{ reason_es, suggested_ref }`. `reason_es` is a friendly Spanish line ("¿Me dejas ver la foto de tu Monstera? Así te digo mejor qué le pasa."); `suggested_ref` tells the app which photo to send (`{kind: "journal_entry", id}` or `{kind: "plant_latest", plant_id}`). Asking is free — it costs one text-only Gemini call, the same `/chat` always makes.
  - Vision only happens on an **explicit** client request to a vision endpoint, which the app makes after the user authorizes (the AI-initiated case) or after the user explicitly asks to analyze a photo (the direct case). There is no path where an image reaches Gemini without an explicit `/vision/*` call.
- **Vision endpoints (explicit, gated, audited):**
  - `POST /vision/analyze-stored` (JSON) — the explicit stored-photo analysis. Request: `{ message, plant_id?, image_ref: {kind:"journal_entry", id} | {kind:"plant_latest", plant_id?} }`. The agent resolves the `photo_url` under the user's RLS-scoped client (`journal_entries` lookup by id, or `plants` / latest `journal_entries` for `plant_latest`), downloads the bytes from the public Storage URL, and calls Gemini vision. Returns `200 VisionAnalyzeResponse`.
  - `POST /vision/analyze-upload` (multipart) — the explicit inline analysis, no storage. Request: `image` file part + `message` + optional `plant_id`. The agent reads the bytes into memory (capped), validates MIME/decodability, resizes, calls Gemini vision, discards the bytes. Returns `200 VisionAnalyzeResponse`. A request that includes any "persist this" intent is rejected with `400` — `/vision/analyze-upload` is analyse-only by construction.
  Both endpoints reuse: 002's auth dependency + RLS-scoped Supabase read (for context, when `plant_id` is given), 003's `proposed_action` + `confirm_token` machinery on the reply, and a new shared vision core.
- **Size/cost/safety shaping.** Every image — stored or inline — is validated, capped (max raw bytes, decodability check), and resized/optimised to a configured maximum dimension and JPEG quality **before** it is sent to Gemini. Allowed MIME: `image/jpeg`, `image/png`, `image/webp`. One image per request in V1.0. A separate vision-capable model setting (`gemini_vision_model`) lets the team pick a vision model without touching the text model used by `/chat`. Imagery that the validator cannot decode returns `400 INVALID_IMAGE`; `vision_max_image_bytes` / `vision_max_dimension` / `vision_jpeg_quality` settings make the cost knobs configurable.
- **Plant health diagnosis and species identification with honesty.** Flora's vision reply is grounded in 002's deep context (watering history, light, recent journal) when a `plant_id` is supplied, so the diagnosis is not a cold read of pixels — it uses the plant's living memory. Structured output from Gemini carries `vision: { kind: "health" | "identify" | "mixed", diagnosis?, possible_species?: [{name, confidence}], confidence: "alta" | "media" | "baja", needs_more_info?: {question_es} }`. When the photo + context are insufficient to diagnose with confidence (the "calibration guidance" roadmap item), Flora returns `confidence: "baja"` and a `needs_more_info.question_es` — she asks for the missing context (ambient light, recent watering, when symptoms started) **instead of inventing** a diagnosis, exactly as `mission.md` requires. Species identification returns ranked candidates with confidence; she is explicit that a photo alone cannot always identify a species to species rank.
- **Off-topic / non-plant image refusal.** The 001 scope guardrail extends to vision: if the analysed image is clearly not a plant or plant-related (a receipt, a selfie, etc.), Flora declines to analyse it and steers back to plants, in Spanish, never accusatory. Structured output expresses this as a `kind: "mixed"` with `needs_more_info` or a short `reply` that declines. The agent does not classify arbitrary images; it stays in its lane.
- **Audit & privacy.** Every vision call emits a structured structlog event: `endpoint` (`analyze-stored` / `analyze-upload`), `source` (`journal_entry` / `plant_latest` / `inline`), `plant_id` (when present), `user.sub`, `mime_type`, `original_bytes`, `resized_bytes`, `max_dimension`, `gemini_model`, `vision_kind`, `confidence`, `status`, `duration_ms`. **Never logged:** image bytes, the resolved Storage URL (it is a private locator even on a public bucket), the photo's decoded pixels, or any journal/text content beyond what 002 already allows. Vision audit events are emitted on success and on `502 UPSTREAM_ERROR` (Gemini or Storage fetch failure).
- **Contract & docs.** `docs/api-contract.md` documents the new `vision_request` field on the `/chat` response, the two `/vision/*` routes (requests, multipart shape, `200` / `401` / `400 INVALID_IMAGE` / `404 IMAGE_NOT_FOUND` / `502` responses), the `VisionAnalyzeResponse` shape (with the `vision` sub-object and the reused `proposed_action`), the image constraints (allowed MIME, max bytes, one image per request), and the cost-gating rule in plain language ("images are only analysed on an explicit `/vision/*` call; `/chat` never sends image bytes"). `tech-stack.md` gets the new `app/vision/` module, its settings (`gemini_vision_model`, `vision_*` caps), new runtime deps (`pillow`, `httpx` declared explicitly), and reframes the "No image analysis" hard limit as lifted by 004.
- **Tests** for the new behaviour: image validator unit tests (allowed MIME accept, rejected MIME, undecodable → `400`, oversized → `400`, resize caps width/height); resize helper tests (output dimension ≤ cap, JPEG quality applied, palette/alpha flattened to RGB); stored retrieval tests (RLS-resolved → bytes fetched; cross-user/foreign `journal_entry_id` → `404`; `photo_url` null → `404`; `plant_latest` with missing plant → `404`; Supabase failure → `502`); upload endpoint tests (multipart accept; no Supabase write asserted; oversized → `400`; wrong MIME → `400`; one-file-only enforced); `/chat` `vision_request` tests (Flora asks when a photo would help; `vision_request` is `null` when she doesn't need one; `suggested_ref.kind` validated; foreign `plant_id` dropped); vision reply tests (diagnosis shape, identification with ranked candidates + confidence, `needs_more_info` path when context insufficient, off-topic non-plant image declined); `proposed_action` reuses 003 token machinery on a diagnosis reply; 502 on Gemini/storage failure; audit event fields + no-bytes-logged; the full 001/002/003 regression suite still green with vision in flight (auth 401 paths, context RLS deny, data-minimization, action propose/confirm/execute, off-topic refusal, Spanish-only).
- **A reconciled constitution.** `tech-stack.md` lists `app/vision/`, the new settings/env vars, the new deps, and reframes the V1.0 "No image analysis" limit as lifted by 004 (matching the reconciliation pattern 001/002/003 used).

## Why

001 gave Flora a voice, 002 gave her the user's garden to read, 003 let her act on the user's behalf. But a plant companion who can only *read text about* a plant can never truly answer the question the user opens the app for the most: "what's wrong with this leaf?" `%00` of plant-care conversations are visual. Without 004, Flora is permanently asked to diagnose from a verbal description of a yellowing leaf — the exact "inventing answers" failure `mission.md` calls out as never acceptable. The roadmap places 004 right after the read/write loop closes, because until Flora can see, the companion promise ("care for plants like an expert, without needing to be an expert") is only half-met.

But vision is also the most expensive and most abuse-prone capability yet: every image sent to Gemini costs materially more than a text token, and a careless design — auto-attaching every journal photo to every `/chat` turn — would silently burn credits on every conversation whether the user wanted analysis or not. That tension is exactly what the user's framing of the feature names: **the AI must be able to retrieve and analyse images, but images must not arrive automatically**; the AI may *ask* for authorization, the user *grants* it, and only then does a vision call happen. So the design axis for 004 is not "can Flora see?" (she can) — it is "can a bad or wasteful path ever reach a vision call without the user meaning it?" and the answer must be **no**.

Secondary reasons it lands here: it exercises the Storage leg of the Supabase integration for the first time (002 only used PostgREST) and so tests the assumption that the agent can retrieve, under the user's identity, an object the app already uploaded — without ever owning the bucket. And it is the first feature where the **untrusted binary content** of a request matters; the validator + cap + resize pipeline is a new shape of safety surface compared to JSON.

It deliberately does **not** introduce conversation persistence (Non-Goal, restated) or any new write surface: a diagnosis can *propose* saving a tip / a schedule via 003, but the vision endpoints themselves write nothing. Inline uploads are analysed and thrown away by construction.

## Acceptance criteria

- `POST /chat` never sends image bytes to Gemini, regardless of how many photos a plant's journal contains. Its 002-sourced context continues to surface photo metadata only (`photo_count`); no `photo_url`, no Storage URL, no bytes enter the Gemini call. (Asserted in tests by mocking Gemini and inspecting the contents/parts sent.)
- A `/chat` reply where Flora decides a photo would help returns `200` with the usual Spanish `reply`, the usual optional `proposed_action` (003), **and** an optional `vision_request: { reason_es, suggested_ref }` whose `reason_es` is a Spanish question asking the user to share a photo, and whose `suggested_ref.kind` is one of `journal_entry` (with `id`) or `plant_latest` (with `plant_id`). When `plant_id` is supplied on the request and `suggested_ref.plant_id` differs, the `vision_request` is dropped (no asking about a foreign plant).
- A `/chat` reply where Flora does not need a photo returns `200` with `vision_request: null` and behaves identically to today (text-only, Spanish, off-topic refusal intact, `proposed_action` semantics intact). Asking for a photo is optional, never forced.
- `POST /vision/analyze-stored` with a valid `Authorization` header and a `journal_entry` `image_ref` resolving to a row the user owns (RLS returns it) returns `200 VisionAnalyzeResponse` whose `reply` is Spanish and on-brand, whose `vision` sub-object has the diagnosis/identification/confidence shape, and whose `proposed_action` (when present) is a valid 003 action with a `confirm_token` minted under the caller's `sub`.
- `POST /vision/analyze-stored` with a `journal_entry` whose `id` belongs to another user (RLS returns no row), or whose `photo_url` is null, returns `404 IMAGE_NOT_FOUND` and performs **no** Gemini call and **no** log of a URL.
- `POST /vision/analyze-stored` with an unknown `suggested_ref.kind` (not `journal_entry`/`plant_latest`) returns `400 INVALID_IMAGE` and performs no fetch.
- `POST /vision/analyze-upload` with a valid `Authorization` header, one allowed-MIME image part (`image/jpeg` | `image/png` | `image/webp`), a `message` (1–2000), and an optional `plant_id`, returns `200 VisionAnalyzeResponse` exactly the same shape as the stored endpoint. The image bytes are **never** written to Supabase or to disk — asserted in tests by mocking the Supabase client and asserting zero `.insert`/`.upload` calls and no filesystem write.
- `POST /vision/analyze-upload` rejects an image whose declared or sniffed MIME is not in the allowlist, or which Pillow cannot decode, with `400 INVALID_IMAGE` and no Gemini call. An image larger than `vision_max_image_bytes` (raw, before resize) is rejected with `400 INVALID_IMAGE`. A request with zero or more than one image part, or with a missing `message`, returns `422` (FastAPI validation) — one image per request is enforced.
- Every image that reaches Gemini (stored or inline) has been resized so that its largest dimension is ≤ `vision_max_dimension` (assert: the bytes passed to the Gemini mock decode to an image with `max(width, height) <= vision_max_dimension`), and re-encoded as JPEG at `vision_jpeg_quality`. The original bytes are dropped after resize.
- A Gemini vision failure (network / 5xx / empty-invalid response) on either vision endpoint returns `502 UPSTREAM_ERROR` with no secret, no URL, and no image bytes in the message; an audit event with `status="upstream_error"` is still emitted.
- An off-topic / non-plant image (asserted via a fixture, e.g. a clear non-plant photo) returns `200` with a Spanish `reply` that declines to analyse it and steers back to plants, and a `vision.kind` that reflects that no diagnosis was produced (e.g. `kind: "mixed"` with `needs_more_info` or an explicit `reply`; the team confirms the exact shape in `plan.md`). The agent never analyses arbitrary non-plant content as if it were a plant.
- A vision call where the photo + context are insufficient for a confident diagnosis returns `200` with `vision.confidence: "baja"` **and** a `vision.needs_more_info.question_es` Spanish clarifying question, and performs **no** `proposed_action` forcing a tip/schedule (Flora asks, she doesn't act on a guess).
- `vision_request` on `/chat` is **never** accompanied by an actual Gemini image call — the `/chat` route is provably text-only. A test inspects the mocked Gemini client and asserts `parts` contain only text on every `/chat` turn, even those returning a non-null `vision_request`.
- Audit log events are emitted on every vision call (success and 502) with the documented fields and **never** contain image bytes, extracted text, the resolved Storage URL, or journal `content`. Asserted against captured log records for both endpoints and the `needs_more_info`/`off-topic` paths.
- `docs/api-contract.md` documents the optional `vision_request` on `/chat`, the `POST /vision/analyze-stored` and `POST /vision/analyze-upload` routes (with the multipart shape and `200`/`401`/`400 INVALID_IMAGE`/`404 IMAGE_NOT_FOUND`/`422`/`502` responses), the `VisionAnalyzeResponse` shape (with the `vision` sub-object and the reused `proposed_action`), the image constraints, and the cost-gating rule, plus the new `400 INVALID_IMAGE` and `404 IMAGE_NOT_FOUND` error codes in the error table.
- `spec/constitution/tech-stack.md` lists `app/vision/`, the new settings (`gemini_vision_model`, `vision_max_image_bytes`, `vision_max_dimension`, `vision_jpeg_quality`, allowed-MIME list), the new runtime deps (`pillow`, `httpx` declared explicitly), and reframes the V1.0 "No image analysis" hard limit as lifted by 004.
- `uv run pytest` passes, including the new vision tests and the full 001/002/003 regression suite. `uv run ruff check` and `uv run ruff format --check` pass.

## Out of reach

Explicitly out of scope for 004; they belong to later features or the constitution:

- **Vision on `/chat` itself (mixing text and image in one call).** By design, image bytes never enter `/chat`. Vision happens only on an explicit `/vision/*` call. A "send a photo alongside a normal message and let Flora decide whether to look" flow is out of reach — it re-introduces exactly the auto-injection the user wants to prevent. Confirm.
- **Multi-image / album analysis.** One image per `/vision/*` request in V1.0. "Compare these two leaves" or "analyse all my Monstera photos" is deferred until usage justifies the cost.
- **Writing images to Supabase from the agent.** The agent never uploads to Storage and never writes `photo_url`. Inline uploads are analyse-and-discard; persistence of an uploaded photo is the app's job, done outside the agent (matches "the agent does not own schema/storage"). A `proposed_action` may ask the user to save a *tip* (text) via 003's `add_journal_entry`, never to save the image itself.
- **Auto-attaching journal photos to `/chat` context.** 002 deliberately sends photo metadata only; 004 does not change that. If a future feature wants photos in `/chat` context, it gets its own gating discussion.
- **Private bucket / signed-URL retrieval.** V1.0 fetches from the existing **public** `plant-photos` bucket by HTTP GET of the URL resolved under RLS. Switching to a private bucket (with Storage signed URLs minted via the user's access token) is a small follow-up flagged in `plan.md` Risks, not engineered here unless the bucket is already private.
- **Streaming / dynamic statuses (005).** Vision endpoints stay single-shot, same envelope as `/chat`. The "Analizando la foto…" status belongs to 005, not 004.
- **Web search for diagnoses (006).** Vision answers are grounded in 002's context + Gemini's vision model only. Cross-referencing pests/diseases against live web sources is deferred to 006.
- **A durable Supabase audit table for vision calls.** Same decision as 003: vision audit lives in agent-side structured logs (Cloud Logging durable), not a Supabase table. The agent does not own schema.
- **Specialised diagnosis models.** The Backlog lists them; 004 uses the general Gemini vision model, not a bespoke plant-disease model.
- **Voice / camera-frame continuous analysis.** Out of scope; 004 is single still images only.
