# 003 - Supabase Write Actions

**Status:** Planning

## What makes

This feature lets Flora close the loop: instead of only *talking about* the user's plants, she can *change* their record on the user's behalf — but only after the user explicitly confirms. It keeps 002's privacy posture (writes run under the user's identity through Row Level Security, never a service-role key) and adds the missing half: a two-step propose → confirm → execute flow that turns a useful reply into a durable change in Supabase.

Concretely it delivers:

- **A writable surface — explicit and allowlisted.** The agent may only write a small, enumerated set of `(table, operation, fields)`. For V1.0 this is:
  - `watering_schedules` — **create** a new active schedule for a plant (the example flow); creating a new active schedule deactivates the user's prior active schedule for that plant.
  - `journal_entries` — **create** a log entry (covers the "save-a-tip" flow: a useful snippet saved as an `observation` entry on a plant's journal; also lets Flora log a watering the user just told her about).
  Nothing else is writable in 003 — `plants`, `light_measurements`, `ai_conversations`/`ai_messages` are explicitly **not** on the surface (conversation persistence is a Non-Goal; plant metadata editing and light readings are deferred). The allowlist lives in code (`app/actions/registry.py`) and is enforced at the confirm endpoint; an out-of-allowlist confirmation returns `400 INVALID_ACTION`, never a silent write.
- **A proposed-action flow inside `/chat`.** Flora's conversation reply stays a single Spanish string (001/002 voice untouched). When she judges an action is useful *and* the user's intent points at it, the `POST /chat` response additionally carries an optional `proposed_action` object: `{ action_type, plant_id, title, summary_es, payload, confirm_token }`. `action_type` is one of the allowlisted verbs (`create_watering_schedule`, `add_journal_entry`); `summary_es` is a human-readable Spanish line the app can show in a confirm card ("Crear riego cada 7 días para tu Monstera"); `payload` is the concrete data to write; `confirm_token` is a server-signed, short-lived token binding that exact payload to that user (see Decisions). No action is written by `/chat` — proposing is side-effect-free.
- **A confirm-and-execute endpoint.** `POST /actions/execute` takes `{ action_type, plant_id, payload, confirm_token }` plus the same `Authorization: Bearer` header as `/chat`. The agent verifies the user (reuse 002's auth dependency), verifies the `confirm_token` (HMAC with a server secret, payload hash + `sub` + expiry, tamper-evident), checks the action against the allowlist, builds the **same user-scoped Supabase client 002 uses**, and performs the write — exactly once. Returns `201 {"action_id": "...", "action_type": "...", "status": "executed"}`. A token that is missing/expired/tampered/for another user returns `401 UNAUTHORIZED`; a payload the app altered after the proposal returns `400 INVALID_ACTION` (hash mismatch); a Supabase failure returns `502 UPSTREAM_ERROR` (reusing 002's envelope); an unsupported `action_type` returns `400 INVALID_ACTION`.
- **Writes under the user's identity — RLS / `user_id` ownership.** Every insert goes through the user's access token, so PostgREST re-verifies the JWT and the row's `user_id` resolves to `auth.uid()`. RLS `INSERT` policies on `watering_schedules` and `journal_entries` (verified in `users-tasks.md`) are the fence; the agent never writes with the service-role key and never sets `user_id` from the request body (the database default / RLS sets owner). Defense-in-depth, same posture as 002.
- **Example flow — watering schedule.** The user asks how often to water their Monstera. Flora answers (using 002's deep context, including the plant's existing schedule), explains the reasoning, and *offers* to set up a 7-day schedule. The `/chat` response carries a `proposed_action` of type `create_watering_schedule` with `frequency_days=7`, `plant_id`, a computed `next_due_at`, and a Spanish summary. The app shows a confirm card; the user taps confirm; the app calls `POST /actions/execute`; the agent writes the new schedule and deactivates the old one, all under the user's RLS-scoped token. Flora's original reply already said what she would do, so nothing happens behind the user's back.
- **Save-a-tip flow.** After any reply, the user can save a useful snippet of Flora's answer into a plant's journal before the conversation disappears (Non-Goal: conversation persistence). Concretely: the app selects text (or just sends "save this") with a `plant_id`; `/chat` (or a dedicated `POST /actions/propose` helper) returns a `proposed_action` of type `add_journal_entry` with `type="observation"` and the snippet as `content`; the user confirms; the agent inserts the journal entry. This is the mechanism the Non-Goals section calls out as *the reason* the write-back feature exists.
- **Audit logging.** Every executed write is logged as a structured event: `action_type`, `table`, `plant_id`, `action_id` (the created row id), `user.sub`, `status`, `duration_ms`, and a short `payload_digest` (hash, never the full content for journal text — privacy). Emitted via the existing structlog JSON pipeline to stdout (Cloud Run captures it). This is the audit trail for "what the AI wrote on whose behalf." No separate Supabase audit table in 003 (the agent does not own the database; a durable audit row is a later decision — see Out of reach).
- **Contract & docs.** `docs/api-contract.md` documents the `proposed_action` field on the `/chat` response, the `POST /actions/execute` route, the new `400 INVALID_ACTION` code, the `confirm_token` model, and the writable-surface allowlist. `tech-stack.md` gets the new `app/actions/` module, the `ACTION_SIGNING_SECRET` setting, and action-related env vars.
- **Tests** for the new behavior: `/chat` returns a `proposed_action` when Flora elects one (and not when she doesn't); `proposed_action` payload matches the allowlist shapes; confirm endpoint: missing/expired/tampered/foreign-user token → 401; app-altered payload → 400; unsupported `action_type` → 400; happy path inserts via the user-scoped client (RLS `INSERT` enforced — asserted the write uses the access token, never a service-role key); watering-schedule flow deactivates the old active schedule; save-a-tip inserts an `observation` journal entry; Supabase failure → 502; audit log is emitted with the right fields and never contains journal `content`; 001/002 regressions still pass with actions in flight.
- **A reconciled constitution.** `tech-stack.md` lists `app/actions/`, the new settings, and reframes the "No writes" stance as lifted by 003 (matching the pattern 001/002 used to lift earlier V0.1 limits).

## Why

002 made Flora *read* the user's garden, so her replies stopped being generic. But a companion that only observes is half a companion: the moment she recommends "water every 7 days," the natural next step is "want me to set that up for you?" — and right now the user has to leave Flora and do it by hand. That hand-off is exactly the kind of friction `mission.md` calls out: the app should *reduce* mental load, not force the user to translate a friendly suggestion into a manual form. 003 is the feature the roadmap places between read-access and the flashier features (image, web search) precisely because it closes the core loop of the companion: **understand → advise → act, with consent.**

It is also the feature the Non-Goals section depends on. The roadmap states conversation persistence is a Non-Goal *because* "useful outputs are saved by the user into Supabase (a tip, a journal entry, a watering schedule) — the conversation itself disappears. This is why the write-back feature (#003) exists." Without 003, the Non-Goal is uncompensated: useful answers evaporate with the chat. The save-a-tip flow is the compensation mechanism.

Security/privacy is the dominant design axis again — now with higher stakes, because writes are mutations of someone else's data. A buggy or unguarded write could create a watering schedule on the wrong user's plant, log a fabricated entry, or let the app fabricate an action the AI never proposed. So the design is **"never write without explicit user consent, never write outside an allowlist, never write under any identity but the user's, and prove the action came from Flora."** The `confirm_token` is what proves provenance; the allowlist is what proves scope; RLS is what proves ownership.

## Acceptance criteria

- A `/chat` reply that includes actionable intent (e.g. the user asks to set up watering, or to save a tip) returns a `200` body with both `reply` (Spanish, on-brand per 001/002) **and** a non-null `proposed_action` whose `action_type` is in the allowlist (`create_watering_schedule` or `add_journal_entry`), whose `payload` matches the schema for that action, whose `plant_id` is a plant the user owns (no foreign `plant_id` ever proposed — RLS-driven empty context means Flora wouldn't propose for a plant she can't see), and whose `summary_es` is a Spanish confirmation line.
- A `/chat` reply with no actionable intent returns `200 {"reply": "..."}` with `proposed_action: null` — Flora never forces an action; proposing is optional.
- `POST /actions/execute` with a valid `confirm_token`, a matching payload, a valid `Authorization` header, and an allowlisted `action_type` returns `201 {"action_id": "...", "action_type": "...", "status": "executed"}` and performs exactly one write to Supabase through the **user-scoped** client.
- `POST /actions/execute` without an `Authorization` header, or with an expired/malformed token, returns `401 UNAUTHORIZED`.
- `POST /actions/execute` with a `confirm_token` that is **expired**, **tampered**, **signed for another user (`sub` mismatch)**, or **reused after execution** returns `401 UNAUTHORIZED` (the token is single-use and short-lived).
- `POST /actions/execute` with a payload whose hash does not match the hash bound into the `confirm_token` (i.e. the app altered `payload` or `plant_id` after the proposal) returns `400 INVALID_ACTION` and performs **no** write.
- `POST /actions/execute` with an `action_type` not in the allowlist (e.g. `delete_plant`, `update_user`) returns `400 INVALID_ACTION` and performs no write.
- A watering-schedule execute deactivates the user's prior active `watering_schedules` row for that `plant_id` and inserts the new active one, as a single logical operation; both writes go through the user-scoped token; the returned `action_id` is the new schedule's id.
- A save-a-tip execute inserts a `journal_entries` row with `type="observation"`, the snippet as `content`, the chosen `plant_id`, and `user_id` resolved by the database/RLS (never supplied by the request body).
- Every write path asserts (in tests) that it is performed through the user access token, never a service-role key.
- A Supabase API failure (network / 5xx) on an execute returns `502 UPSTREAM_ERROR` with no token or secret in the message, and no partial write is committed (the deactivation + insert are ordered so a mid-flow failure leaves the old schedule active, or the whole thing fails atomically — see Decisions).
- An audit log event is emitted on every executed write (success and 502 failure) containing `action_type`, `table`, `plant_id`, `action_id` (when available), `user.sub`, `status`, `duration_ms`, and a `payload_digest` hash; for `add_journal_entry` the event **never** contains the `content` text (privacy). Logged via the existing structlog pipeline.
- `docs/api-contract.md` documents the optional `proposed_action` on `/chat`, the `POST /actions/execute` route (request + `201`/`401`/`400`/`502` responses), the `confirm_token` model, the new `400 INVALID_ACTION` error code, and the writable-surface allowlist with the two V1.0 verbs.
- `spec/constitution/tech-stack.md` lists `app/actions/`, the new settings (`action_signing_secret`, action ttl), the new env vars, and reframes the V0.1 "no writes" limit as lifted by 003.
- `uv run pytest` passes, including new propose/confirm tests and the 001/002 regression suite (auth, context, RLS deny, minimization, off-topic refusal, Spanish-only) with actions in flight.
- `uv run ruff check` and `uv run ruff format --check` pass.

## Out of reach

Explicitly out of scope for 003; they belong to later features or the constitution:

- **Deletions and updates of arbitrary fields.** 003 only *creates*. Deleting a plant, editing `plants.name`/`species`/`location`, editing a journal entry's text, or cancelling a schedule by deleting it are out of scope. Cancelling a schedule is approximated in 003 by setting a new one, but a dedicated delete/update surface is deferred (it widens the attack surface and needs its own design). Toggling `watering_schedules.active=false` directly is a reasonable follow-up but is **not** in V1.0 of 003 unless the example flow demands it (see Decisions).
- **Light measurements writes.** `light_measurements` is device/app-driven, not AI-driven; writing calibrated-light rows from a conversation would be inventing data. Out of scope (matches `mission.md`'s "never invent answers").
- **Conversation persistence (Non-Goal, restated).** `ai_conversations` / `ai_messages` are **read-only** to the agent in 003. The save-a-tip flow writes a `journal_entries` row, not a chat transcript. The conversation still disappears; only its useful tip survives.
- **Image content analysis (004).** Proposed actions never carry an image; `add_journal_entry` `photo_url` is left null in 003 (the app can attach a photo later). Diagnoses from photos land in 004.
- **Web search (006).** Proposed actions are grounded only in 002's context + Flora's knowledge. No external sourcing of the action payload yet.
- **Streaming / dynamic statuses (005).** Both `/chat` and `/actions/execute` stay single-shot. A confirm does not stream intermediate statuses.
- **A durable Supabase audit table.** 003's audit trail is agent-side structured logs (durable via Cloud Logging), **not** a Supabase table. Writing an `agent_actions` row in the user's database would be the agent owning schema, which `mission.md` says it doesn't. A durable DB-backed audit trail is a later, app-team-owned decision.
- **Multi-action batching.** One `proposed_action` per `/chat` reply; one write per `/actions/execute` call. Batching ("set up watering for all my plants") is deferred until usage justifies it.
- **Confirmation UX in the agent.** The agent proposes; the app owns the confirm card. 003 defines the *payload contract* for that card but not its visual design.
- **Off-topic action refusal as a separate test matrix.** The 001 off-topic guardrail already prevents Flora from proposing actions for non-plant topics; no new matrix is needed, the existing refusal tests must simply still pass once actions are in flight.
